Zscaler · Data Engineer · 2024–2025

Compiling Salesforce formulas into incremental SQL

Formula fields recompute without touching LastModified, so incremental loads missed changes and fell back to full refreshes. A metadata compiler walks each formula’s dependency graph depth-first, has an LLM emit SQL from that structured context, and lands it in versioned dbt models fed by Matillion upserts. Sampled rows are reconciled against live CRM before anything deploys.

  • ~80% lower reporting latency
  • ~35% faster queries
  • LLM → SQL reconciled vs live CRM
Technical deep dive

Problem

Leadership dashboards and adoption metrics depended on Salesforce data whose formula fields recalculate in real time but never update LastModifiedTimestamp. Incremental logic broke, full-table refreshes raised latency and warehouse cost, and nested, undocumented field dependencies left no way to trace impact.

Metadata compiler

  • Pull formula definitions through the Salesforce ObjectDetails API.
  • Depth-first traversal maps every upstream field dependency; each formula gets a structured JSON context.
  • The dependency graph and formula logic go to an LLM, which generates SQL; output lands in dbt models, so the logic becomes deterministic, versioned and reviewable.

Ingestion

  • Change detection and incremental upserts replace full-table refreshes; modular transformation layers.
  • Partitioning and Snowflake clustering for location attributes cut scan volume on spatial-style queries.

Verification

  • Because LLM-generated SQL is a risk, automated sampling compares warehouse output with the live CRM and flags discrepancies programmatically; reconciliation dashboards track it.
  • Git workflows with automated schema checks and SQL tests in GitHub Actions; Docker for consistent environments.

Also

API integrations for LinkedIn Campaign, Asana and Jira, normalized into the warehouse for marketing and delivery dashboards. Stack: Python, SQL, Snowflake, dbt, Matillion, AWS (S3, EC2), Docker, GitHub Actions.

LatentView Analytics · Data Engineer · 2021–2023

An 800 TB HDFS → S3 migration with a test gate

AWS DataSync moved the data while bash scripts tracked every copied batch. A Python/pytest framework diffed source and destination for row mismatches, null anomalies and type drift before go-live. Legacy Airflow moved to MWAA-style DAGs, and CloudWatch → SNS → Lambda enforced SLAs.

  • ~800 TB migrated
  • 99.6% validation accuracy
  • ~45% fewer client escalations
  • 18 → 6 min one reporting model
Technical deep dive

Risks at this scale

Corruption in transit, schema drift, partial ingestion, silent batch-job errors and SLA breaches on client reporting.

Validation framework

  • Delta Lake patterns to track changes; Python validation logic with pytest-style dataset tests.
  • Programmatic source-vs-destination comparison: row mismatches, null anomalies, type inconsistencies, all flagged before release.

Monitoring and SLAs

CloudWatch metrics, SNS alerting and Lambda triggers on top of Airflow detect SLA breaches and job failures and log root-cause traces, which cut client escalations by about 45%.

Orchestration

Legacy Airflow upgraded to managed MWAA-style patterns: containerized operators, modular DAGs, isolated per-workflow tests, better retries, fewer failed deploys.

Performance

Layered CTEs restructured, partitioning re-planned (pruning instead of wide scans), resources and query plans tuned: one major reporting model went from about 18 to 6 minutes. Stack: Python, Spark/Databricks, Snowflake, S3, Lambda, CloudWatch, Airflow.
