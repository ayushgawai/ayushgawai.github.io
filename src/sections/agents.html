Chatbots and agent fleets with guardrails

Conversation is the surface, not the system: grounded context, read-only answers, fenced untrusted text, and a human approval gate at the end. The second sketch is a whole fleet of coding agents that only lands a fix when the real owners sign off.

The guardrail is the design

The model has no execution tools. It cannot rerun miners, change configuration, run arbitrary queries, or trigger actions — it can only read the same published weekly snapshot the dashboard reads, and the answer is read-only.

  • Fenced context. report data and user questions are both treated as untrusted content, wrapped in fences so instructions inside them stay data.
  • Bounded everything. question length, report context and response length are all capped; for large reports the context is trimmed to the relevant miners and owners.
  • Report-week grounding. every answer is pinned to the published report it came from. If the report can't answer it, the answer says so.

Conversational analytics kept inside a constrained security boundary: the bot can explain the fleet, it cannot act on it.

One rename, three repos, six failures

Built with Manav Patel — a WeMakeDevs submission, November 2026. The question it answers: if I rename a field in an upstream event schema, which downstream repos, dbt models, ML features and dashboards break before I merge?

An upstream PR renames user_id to account_id and posts to the schema-changes room. An impact coordinator broadcasts the impact-checker role to three linked rooms; three coding agents — Claude Code, Codex and OpenCode — work in their own checkouts and run the upstream branch against local tests. Six checks fail. The agents open Jira tickets and three coordinated fix PRs. The merge gate holds pending: a non-owner's approval is rejected, and only the real owners turn the pipeline green.

Parallel agents with bounded ownership, independent tests, an audit trail, least privilege — and a human-controlled merge gate.
