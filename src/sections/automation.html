Make the system tell people, so they don’t have to check

The perception data-mining fleet runs ~400 miners producing on the order of 90M events a week. The boring question is “is it still working?” Two mechanisms answer it: a scheduled one and an event-driven one — and the sketch runs both.

Two mechanisms, one philosophy

Scheduled — the weekly fleet report. A gear turns once a week, aggregates runs, failures and mined volume, and writes one immutable JSON snapshot to S3. The static dashboard, the Slack digest and each owner’s DM all read the same published artifact: compute once, publish once, serve many.

Event-driven — near-real-time failure alerts. The tripwire sits exactly where a run’s state changes: when a run flips to FAILED, the bell rings and an alert with a deep link is out within minutes. Opt-in per miner, default off, so noisy backfills don’t page the team.

Failure discovery moved from days (a periodic team review) to minutes.

Sneakstore.in, the shop-floor version

Before the data jobs: as founder of Sneakstore.in (2020–22), a bootstrapped sneaker resale turned e-commerce, the same idea showed up at the register. Every order, payment and shipment below is a small automation that made the shop run itself.

Ran paid Instagram, Facebook and Google Ads daily for two years, A/B testing creatives and audiences while tracking ROAS.

order → paid → shipped → tracked — no one touches it

  1. order

    Customer buys on the store; WooCommerce emits the order event.

  2. payment

    Instamojo webhook confirms it, and the payment is reconciled against the ledger before anything ships.

  3. shipment

    A Shiprocket shipment is created automatically; the tracking ID is generated with no manual courier step.

  4. tracking

    Shipping status syncs back to the customer. Funnel and cohort dashboards plus A/B tests decide what to change next.

Feb 2020 – Aug 2022 · bootstrapped · first-hand measurement of channels, funnels, ROAS.
