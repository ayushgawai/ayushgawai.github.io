Ground-truth precision for every miner

Deterministic routing maps each miner to its labeling view; an LLM grounded in the ontology and live label vocabulary drafts a SQL true-positive predicate that is executed and verified before it is stored. Scoring is then plain SQL over the full labeled population, with the canonical SQL kept beside every number.

Technical deep dive

Problem

~409 active miners mined 90M+ events a week from drive logs (pedestrians, vehicles, signs, attributes such as reverse lights). Every event already went to human annotation, but quality checks were manual and miner by miner. Each miner targets something different and each annotation task encodes labels differently, so no single "true positive" query existed.

Predicate authoring: the only LLM step

  • miner → annotation task → task type → labeling view is a deterministic mapping across classification, 2D detection, instance, track-attribute, sound-interval and 3D-cuboid tasks. A hallucinated view would give a valid but wrong number, so routing never touches the LLM.
  • Grounding: miner description and selection config, annotation ontology, valid label keys and the label vocabulary actually observed in the warehouse. Output: one scoped SQL boolean predicate.
  • generate → execute → verify → retry: invalid SQL, unsupported fields, zero matches or vocabulary conflicts go back into the next grounded attempt.

Scoring and storage

  • precision = true-positive labeled events / effective generated events (canceled and failed downloads excluded), counted over the whole labeled population in Databricks SQL. No sampling, zero extra labeling cost.
  • Each result stores precision, TP, denominator, labeled count, lifecycle funnel, labeling view and the canonical SQL. TP ≤ labeled ≤ denominator is checked and stored SQL is re-run to reproduce numbers.
  • Write-on-change history: a new row only when TP or the denominator changes, ~93% fewer writes between sweeps, so the table records quality changes instead of heartbeats.
  • Latest precision for a page of the miner table comes from one ROW_NUMBER() OVER (PARTITION BY miner ORDER BY created_at DESC) query: no N+1, no warehouse call on the request path.
  • Coverage audit: some warehouse views missed events (overwrite rebuilds, enrichment joins dropping runs, raw-landing gaps). Missing labels can hide true positives but never invent them, so stored precision is a lower bound.

Fleet operation

  • Scheduled Airflow sweep with per-miner failure isolation and a non-zero exit for alerting: 409 active, 353 with generated configs, 321 GT-capable, 321 validated, no backlog. Rehearsed on ~261 staging miners first.
  • GT (exact, once labels exist) and VLM (sampled, for new miners) are two first-class methods behind one polymorphic config and a FastAPI endpoint that runs either independently.
  • Weekly Postgres aggregation into immutable, versioned JSON snapshots plus a manifest in S3, read by a zero-backend Vite/TypeScript/Chart.js dashboard, a Slack digest and per-owner DMs.
  • Failure alerts fire on the miner run-state transition to FAILED (event-driven, opt-in per miner): discovery went from days to minutes. A read-only Slack Q&A answers only from published snapshots: no tools, fenced untrusted context, bounded lengths, Vault-managed credentials.

Delivery

~14 PRs in small deployable slices; validation alone was four (config generation, GT execution and persistence, fleet sweep, UI). The rule throughout: LLM proposes → deterministic systems verify → production executes → humans can reproduce.

Technical deep dive
  • Input: 2 s of noisy 10 Hz positions per agent. Output: 3 s of future motion.
  • Physics baselines: constant velocity, a Kalman filter, and CTRV (constant turn rate and velocity) for curved paths.
  • Learned: ridge regression on the observed track, and a multimodal model over a set of anchor trajectories, so a lane change and a straight path can both stay alive.
  • Scenarios: lane changes, braking and turns, evaluated with multi-hypothesis metrics.
