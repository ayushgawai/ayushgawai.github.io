Zoox Perception · data-mining fleet · 2026

Grounded SQL predicates with execute-and-verify

Each miner's precision rule is a SQL predicate over label_bucket, drafted by an LLM from the miner config, annotation task, ontology and the label vocabulary observed in the warehouse. Every draft executes against live label counts and is rejected with that evidence on invalid SQL, unknown fields, empty matches or vocabulary conflicts. Task-to-labeling-view routing stays a deterministic mapping: a hallucinated view would give a valid-looking but wrong precision.

  • ~409 active miners covered
  • 321/321 GT-capable miners validated
  • ~1.3 s median scoring
  • days → min failure discovery
Technical deep dive

The loop

  • Grounded context: miner description and selection config, annotation task, ontology, valid label_key values, and the label vocabulary actually observed in Databricks.
  • Generate a scoped boolean predicate, execute it against live label counts, verify SQL validity, field support, non-empty matches and vocabulary conflicts.
  • Failures return with the observed evidence for another grounded iteration. The accepted predicate is stored as canonical SQL, so anyone can rerun it and reproduce the number.

Key decisions

  • Deterministic code owns routing: miner → annotation task → task type → labeling view. The LLM owns semantic interpretation only. A bad predicate fails visibly; a bad view would not.
  • Population-level precision: true-positive labeled events over effective generated events, excluding canceled and failed-download work.

Results and stack

  • ~409 active miners, 90M+ events mined per week, 321 of 321 GT-capable miners validated, ~93% fewer redundant writes, failure discovery from days to minutes, ~14 PRs.
  • Databricks SQL and an internal LLM API. Internal work, so no public repository.

Sentinel AI: cheap on every frame, VLM only on escalation

YOLO pose detection with per-track motion rules runs on every frame of a multi-camera wall; only credible events escalate, as a 16-frame evidence bundle, to Qwen3-VL served locally on an HP ZGX Nano. Deterministic severity thresholds and an incident state machine decide alerts. I owned the frame-streaming backend, async event routing, alert triggers and incident logging.

Technical deep dive

Ownership

Team project, winner of the HP × SJSU Edge AI Hackathon. I owned the video and frame-streaming backend, asynchronous event routing, alert triggers and incident logging.

Architecture

  • YOLO26s-pose person detection with temporal tracking and per-track motion rules (weapon, fall, run, loitering, sudden change); optional OpenCLIP ViT-B/16 anomaly screening.
  • Score-based escalation instead of a VLM call per frame: a 16-frame event window goes to locally served Qwen3-VL-30B-A3B FP8 on the HP ZGX Nano (GB10) through HP Z Runtime, classifying WEAPON, FIGHT, THEFT, RUN, MEDICAL or BENIGN.
  • Python severity thresholds and an incident state machine: NEW → ALERTED → DISPATCH_PENDING → DISPATCHED → TRACKING → RESOLVED / DISMISSED. SQLite event history; REST, WebSocket and MJPEG console updates.
  • Guarded dispatch path: local ASR + TTS + telephony, human confirmation, kill switch, one dispatch per incident, fixed camera-to-address map.

Demo observations (not benchmarks)

  • The six-feed wall (three with full analysis) ran about 13–14 fps, up from ~3. Demo calls never reached the real 911 service.

Later variant

Meta SAM 3.1 + Muse: 8-second per-camera ring buffers, ByteTrack IDs through weak detections, SAM prompt-based segmentation on enlarged person crops, 8 evidence frames + crop to Muse Spark on Baseten, a text-only verifier, and deterministic guardrails deciding automatic versus operator-approved dispatch.

LEO satellite coverage risk · 2026

A tool-use agent over 4.7 million locations

Scores tree and terrain obstruction risk for LEO satellite service at every North Carolina location. A Claude tool-use orchestrator sequences five deterministic Python tools and passes artifacts as file paths, so millions of rows never enter the context window. A pipeline-only mode runs the same functions with no LLM at all.

  • 4,674,905 locations scored
  • 100/100 counties
  • 250 tests
Code on GitHub
Technical deep dive

Data chain

  • Location coordinates and IDs; NLCD and USGS canopy rasters; USGS 3DEP elevation with derived slope; NLCD land-cover classes.
  • Spatial sampling at each location, component scoring into HIGH / MODERATE / LOW tiers using Starlink installation guidance, validation of coordinates and county coverage.

Agent design

  • Claude tool-use orchestrator over ingest_locations, sample_environment, score_risk, validate_results, generate_report. Python does the geospatial and numeric work; file-based state passes artifact paths, not rows, into the prompt.
  • Interactive tools answer coordinate, address, area, polygon and nearby-alternative questions over the precomputed scores; a web app serves map and search.
  • Pipeline-only mode runs the same functions with no LLM.

March 2026 run

  • All 4,674,905 locations scored, 100 of 100 counties, 0.0% environmental NaNs, tiers HIGH 19.4% / MODERATE 31.3% / LOW 49.3%, 250-test suite.

Zscaler · 2024–2025

Compiling Salesforce formulas into verified dbt SQL

Formula fields recompute without bumping LastModified, so incremental loads silently missed changes. I built a metadata compiler that walks each formula's dependency graph depth-first, serializes it as JSON context for an LLM that emits SQL into versioned dbt models, and samples warehouse output against the live CRM before anything deploys.

  • ~80% lower reporting latency
  • ~35% faster queries
Technical deep dive
  • Formula definitions pulled through the Salesforce ObjectDetails API; depth-first traversal maps every nested field dependency; each formula gets a structured JSON context.
  • The dependency graph plus formula logic go to the LLM, which generates SQL; output lands in dbt models, so the logic is deterministic, versioned and reviewable.
  • Because the SQL is LLM-written, automated sampling compares warehouse output with the live CRM and flags discrepancies programmatically; reconciliation dashboards track it. Git-based CI with schema checks and SQL tests.
  • Stack: Python, SQL, Snowflake, dbt, Matillion, AWS. Internal work, so no public repository.
