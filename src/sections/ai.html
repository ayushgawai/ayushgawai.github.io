The LLM proposes, the machine verifies

Every LLM system here follows one rule. The model drafts, deterministic code checks the draft against real data, and the accepted result is stored so anyone can rerun it and get the same number. The model is a constrained author, never the source of truth.

Why a loop, and not just a prompt

At Zoox, a few hundred data miners each needed a rule for what counts as a true positive. Generation was grounded: the model saw the miner's description and config, the annotation task and ontology, the valid label_key values and the label vocabulary actually observed in the warehouse.

  • Executed, then verified. Each candidate ran against live label counts. Invalid SQL, unknown fields, empty matches or vocabulary conflicts went back with the observed evidence for another draft.
  • Routing never touches the LLM. Miner to task to labeling view is a deterministic mapping. A hallucinated predicate fails visibly; a hallucinated view would give a valid-looking but wrong precision.
  • The model steps out. Once a predicate is filed, scoring is stored SQL, about 1.3 s median per miner, and anyone can rerun it for the same number.
