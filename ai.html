Zoox Perception · data-mining fleet · 2026

Grounded SQL predicates with execute-and-verify

Each miner's precision rule is a SQL predicate over label_bucket, drafted by an LLM from the miner config, annotation task, ontology and the label vocabulary observed in the warehouse. Every draft executes against live label counts and is rejected with that evidence on invalid SQL, unknown fields, empty matches or vocabulary conflicts. Task-to-labeling-view routing stays a deterministic mapping: a hallucinated view would give a valid-looking but wrong precision.

  • ~409 active miners covered
  • 321/321 GT-capable miners validated
  • ~1.3 s median scoring
  • days → min failure discovery
More in the Autonomy chapter
Technical deep dive

The loop

  • Grounded context: miner description and selection config, annotation task, ontology, valid label_key values, and the label vocabulary actually observed in Databricks.
  • Generate a scoped boolean predicate, execute it against live label counts, verify SQL validity, field support, non-empty matches and vocabulary conflicts.
  • Failures return with the observed evidence for another grounded iteration. The accepted predicate is stored as canonical SQL, so anyone can rerun it and reproduce the number.

Key decisions

  • Deterministic code owns routing: miner → annotation task → task type → labeling view. The LLM owns semantic interpretation only. A bad predicate fails visibly; a bad view would not.
  • Population-level precision: true-positive labeled events over effective generated events, excluding canceled and failed-download work.

Results and stack

  • ~409 active miners, 90M+ events mined per week, 321 of 321 GT-capable miners validated, ~93% fewer redundant writes, failure discovery from days to minutes, ~14 PRs.
  • Databricks SQL and an internal LLM API. Internal work, so no public repository.

Technical deep dive

Scheduled: weekly fleet report

  • Flow: platform Postgres → Python/SQL aggregation → performance_report_<week>.json → S3 → manifest.json → dashboard and Slack. Deployed as a recurring Airflow workload.
  • Metrics over the previous complete Monday-to-Monday window: active miners, runs, success and failure rates, mined-event volume, owner- and miner-level performance, validation precision, failure concentration, week-over-week comparisons.
  • Snapshots are immutable once published; the manifest gives the dashboard the available history. Computation is separated from presentation: the expensive aggregation runs once and every consumer reads the same artifact.

Zero-backend dashboard

Vite + TypeScript + Chart.js, static HTML/CSS loading the published snapshots directly. No application backend: cheap to serve, reproducible, and isolated from the production platform. Fleet KPI cards, a filterable and sortable miner table, owner and miner filters, computed insights (miners driving disproportionate failures, high-volume miners with low precision, week-over-week trends), detail drawers and shareable URL state.

Push delivery

  • A shared Slack notification utility with a Vault-backed bot token and least-privilege policies became the delivery primitive for digests, owner summaries, failure alerts and interactive tooling.
  • The weekly digest posts fleet health, volume, failures, precision and notable miners with dashboard links; each owner gets a DM of only their miners with a dashboard link pre-filtered to their scope.

Event-driven: failure alerts

  • Notification logic sits in the miner run-state transition: on FAILED the owner or channel gets miner identity, run ID, state, timestamp and a deep link to the run.
  • Why not poll: the transition is the most accurate place to detect failure. Hooking it cut detection latency, duplicate logic and unnecessary database scans. Weekly analytics stay scheduled; failures are delivered on the event.
  • Opt-in control: a per-miner notification key in the miner config, exposed in the UI with a precise read-modify-write of only that key so other settings stay untouched. A missing key means opted out, so noisy backfills and experiments stay quiet without a new config database.

Internal work, so no public repository.

Technical deep dive

Threat model

Anyone in Slack can type a question, and report fields carry free text written by many owners. Either can contain instructions. The design assumes both are hostile and removes the capability an attacker would want, instead of trying to filter every phrasing.

Guardrails, as built

  • Data path: published weekly JSON snapshot (the same one the dashboard reads) → context selection → internal LLM API → text answer.
  • Fenced context: report data is wrapped as untrusted content and the question as untrusted instructions; instructions inside either stay data.
  • Bounded lengths on the question, the report context and the response. Large reports are trimmed to the relevant miners and owners, with compact history kept for trend questions.
  • No execution tools: the model cannot rerun jobs, modify configuration, run arbitrary queries or trigger operations. Answers are grounded to the report week.
  • Credentials: the bot token and API keys come from Vault under explicit least-privilege policies, never from config files.

Where the habit came from

At Zscaler (data engineer, Jan 2024 – Jul 2025) the work was reporting accuracy and secure environment management for product, security and GTM teams. Internal work, so no public repository.
