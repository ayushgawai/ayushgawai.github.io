BART + VTA real-time feeds to an operator dashboard

GTFS static and GTFS-realtime feeds enter through a Kafka producer/consumer; three Airflow DAGs on AWS MWAA load Snowflake landing and analytics schemas, and dbt builds route-level performance aggregates. FastAPI serves a React/TypeScript dashboard, with heavy ETL and model training kept off the read path.

Technical deep dive

Team capstone. I ran the pipeline on AWS S3 and MWAA, and built the Azure Databricks extension.

Data flow

  • Sources: BART and VTA GTFS schedules plus GTFS-realtime vehicle feeds.
  • Kafka producer and consumer carry near-real-time vehicle events.
  • Airflow DAGs: GTFS incremental ingestion, streaming ingestion, ML forecasting.
  • Snowflake landing and analytics schemas; dbt transformations, forecast models and route-level performance aggregates.
  • FastAPI REST layer feeding React/TypeScript dashboards with maps, metrics and natural-language query assistance. Docker Compose; credentials in AWS Secrets Manager.

Hard parts

  • Static stop IDs don’t line up with live events, so events are aligned to the static schedule before loading.
  • Late and malformed location samples: dedup and replay instead of trusting arrival order.
  • Fast API responses without putting ETL or training on the dashboard path.

Azure extension

On-time performance and service-reliability KPIs modeled in Azure Databricks (PySpark, Delta Lake), orchestrated by Azure Data Factory, with SQL data quality checks and Power BI reporting.
