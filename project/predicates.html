Grounded SQL predicates

Quality validation for ~409 active perception data miners: the LLM drafts a SQL true-positive predicate, the system executes and verifies it, and scoring is plain SQL over the full labeled population.

how it works

  • Deterministic routing: miner → annotation task → task type → labeling view is a fixed mapping across classification, 2D detection, instance, track-attribute, sound-interval and 3D-cuboid tasks. A hallucinated view would produce a valid but wrong number, so routing never touches the LLM.
  • Grounding: the draft sees the miner description and selection config, the annotation ontology, valid label keys and the label vocabulary actually observed in the warehouse. Output: one scoped SQL boolean predicate.
  • Generate → execute → verify → retry: invalid SQL, unsupported fields, zero matches or vocabulary conflicts loop back into the next grounded attempt. The LLM only writes the rule; scoring never calls it.
  • Scoring stores precision, TP, denominator, labeled count, the lifecycle funnel, the labeling view and the canonical SQL. A new row is written only when TP or the denominator changes (~93% fewer writes).
  • Distribution: weekly Postgres aggregation into immutable versioned JSON snapshots plus an S3 manifest, read by a zero-backend Vite/TypeScript/Chart.js dashboard, a Slack digest and per-owner DMs. Failure alerts fire on the FAILED run-state transition.

the design calls

LLM proposes, deterministic verifies

Every number ships with the SQL that reproduces it; stored precision is a lower bound, and coverage gaps are audited.
